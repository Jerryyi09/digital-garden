## 现状与断层（架构方已查明，执行方不必重新调查）

| | 旧流程（现存 4 本，用户认可的逐句跟读） | 新流程（96 本，现状） |
|---|---|---|
| 识别 | `word_timestamps=True`，逐词时间戳 | `word_timestamps=False`，只有分段时间戳 |
| 正文锚点 | 按句和短语切分（例：`…-segment29`="ideal"，`…-segment30`="without ever realizing."） | 按段落切分，长段再粗切 |
| 每次高亮时长 | 中位约 2 秒 | 中位约 16–20 秒，一整段 |
| 引擎标识 | `whisper-word-global-monotone-exact-v1` | `fast-paragraph-v1` |

旧流程的 4 本：`心智成长/101 Essays That Will Change The Way You Think`、`Clear Thinking`、`Make Your Bed`、`Think Like a Psychologist`。

**断层的成因**（手册 25 §第 120–124 行，§181–191 行）：早期把"逐词 ≤200ms 声学认证"当作上线门槛，导致全库判为失败；改用个人 5% 标准时，**把逐词时间戳这项能力也一起拿掉了**，理由是它让 ASR 慢约 35%。真正该放宽的只是认证门槛，不是逐词能力。

**新的事实**（架构方 2026-10-26 实测，Clear Thinking 3600–5400s 块）：批量解码 `transcribe_chunks_batched` 本身支持逐词时间戳：

| 批量 16、静音切窗 | 耗时 | 倍率 |
|---|---|---|
| `word_timestamps=False` | 3.1 s | 581× |
| `word_timestamps=True` | 5.9 s | **307×** |

带逐词时间戳的批量解码，仍然比旧流程的串行解码（约 134–142×）快一倍以上。**速度不再构成放弃逐句的理由。** 逐词结果位于每个窗口记录的顶层 `words` 字段，不在 `segments` 里。

## 方案：粗定位 + 细对齐，两段都复用现成代码

不发明新算法，把两套已经跑通的东西接起来：

1. **段落粗定位**：沿用 `readalong_fast` 现有的段落倒排索引和有界局部比对（`matcher.ParagraphIndex`），用来确定每段识别文本对应 EPUB 的哪个段落。这一层负责抗版本差异、抗漏读，已经过全库验证。
2. **句级细对齐**：在已定位的段落内部，用逐词时间戳把识别出的词和 EPUB 的词做单调对齐，复用旧引擎 `whisper-word-global-monotone-exact-v1` 的对齐逻辑（`tools/readalong/universal_stream_aligner.py` / `aligner.py`），得出每一句的起止时间。
3. **正文按句标注**：复用 `tools/readalong/engine/mark_sentence.py` 的句子和短语切分。超过约 8 秒的长句，按逗号、分号等子句标点继续切开，旧流程的 `-part1/-part2` 就是这样做的。
4. **兜底**：某一句匹配到的词太少、无法给出可靠时间时，这一句沿用所在段落的时间，标记为 `timingStatus=SENTENCE_FROM_PARAGRAPH`。**不得为此丢弃整段**，也不得让这一句没有高亮。

**发布标准不变**：仍然是个人 5% 容错（`personal-readalong-5pct-v1`），不恢复逐词声学认证门槛。

**前端不改**：句级锚点仍是正文里的 `<span id>`，timeline 格式不变，旧流程那 4 本一直是这样显示的。v28 前端（网络优先 Service Worker、去掉失败的外部资源、不再循环加载）已经上线，本工单不碰前端代码。

  3. 以后**禁止直接改写 NUC 上的书籍文件**。任何内容修正都必须走"本地发布 → 版本目录 → 同步 → 核验"。

### 检验方法改革：只验改动的书，按层次由便宜到昂贵
前几轮的全库深度扫描耗时数小时，原因有两个：范围是全库，而不是本次改动的书；方法是对 14,000 多个文件逐个发 Alist HTTP 请求，每个目录还强制刷新缓存。以下规范取代"每次全库 Alist 扫描"：

**第 1 层：本地静态检验**（每本候选经 `publish_practical` 原子发布后立即运行；秒级、零网络）
- manifest 结构完整；`assetRevision` 指向的本地版本目录存在；
- timeline 中每个 `document` 文件都存在，且文件里能找到对应的 `fragment` 锚点；文档路径不含未解码的 `%xx`；
- `audioSources` 中每个文件都存在、大小与指纹一致；`alistPath` 与真实相对路径一致（包括分卷书）；音轨按自然数字序排列；
- 正文里有高亮样式块；
- 粒度指标（高亮时长中位数和 95 分位、兜底占比）达到阈值。
今晚到目前为止踩过的每一个雷，都应当在这一层被拦下，并且全部入库为单元测试。

**第 2 层：同步后服务器文件级核验**（只查本次同步改动的书，所有书合并成**一次** SSH 调用、一个 Python 进程，秒级）
- 改动范围以 rsync 的 `--itemize-changes` 输出为准；
- 在 NUC 文件系统上按 `app.js` 的读取规则判定：版本目录与 `readalong/` 的选择、timeline 能否解析、音源文件是否存在、`audioSourceId` 能否对应；
- 本地与 NUC 的 manifest、timeline 和正文树哈希逐本一致。

**第 3 层：Alist 与前端抽样**（每批只抽 1 本，分钟级）
- 通过 Alist API 取 1 本改动书的 manifest、timeline 和一个正文文件，证明传输层正常。Alist 对所有书的行为相同，抽一本即可；
- 只有当前端、Alist 配置或同步脚本本身发生改动时，才在内置浏览器里实际播放一本作冒烟测试。

**全库巡检**：不随工单执行。
- 每本书在核验通过后保存一份核验收据（manifest、timeline、正文树的哈希加检验时间）。巡检时在 NUC 上单进程重新计算哈希，**只对哈希变化的书重跑第 2 层规则**；全库文件级巡检本身也只需要几十秒。
- 全库 Alist 扫描只在前端、Alist 或同步脚本发生变更后做一次。

**ASR**：缓存以"音频指纹 + 引擎"为键。全库重新识别只在换引擎时发生，本次是一次性成本。之后的映射修订（切句、对齐、兜底规则）一律复用缓存，不重新识别。

**回归**：单元测试、14 个筛查用例、7 本黄金书的粒度指标（只用缓存，不跑新 ASR），合计应在几分钟内完成。
